`BigBird` 是一套面向初学者的 RV32I 处理器教学工程。

它不打算把“从零做 CPU”描述成某种高深莫测的入门仪式，也不打算在第一页就把流水线、异常、前递、暂停、冲刷和一串缩写一起塞给读者。更现实一点的目标是：把学习曲线拆开，把阶段目标说清，把验证路径固定下来，让读者每前进一步，都知道自己到底做成了什么。

如果很多教程的默认节奏是“先挫败，后理解”，那么 `BigBird` 更希望采用的节奏是“先跑通，后理解；先建立直觉，再补齐理论”。

## 这是什么

`BigBird` 是一个完整独立的教学体系，围绕一颗面向 RV32I 基本教学目标的处理器展开。整个项目通过 `v1` 到 `v8` 八个阶段版本，逐步覆盖：

- 最小可运行单周期骨架
- 单周期整数执行主线
- 单周期访存与控制流
- 流水线结构拆分
- 冒险处理
- CSR 与异常返回

我希望每一个版本都至少做到三件事：

- 目标明确
- 代码可读
- 行为可验证

## 先跑起来

考虑到大部分人验证与测试都在虚拟仿真，本次模拟器采用[哈尔滨工业大学（深圳）的trace测试框架](https://github.com/HITSZ-CDP/cdp-tests)

如果你只想先确认环境可用，推荐先跑最小样例。下面的命令默认在 `BigBird` 仓库根目录执行：

```bash
cd cdp-tests
make clean
make run TEST=simple CPU_DIR=../v1
```

如果输出中出现 `Test Point Pass!`，说明当前环境、测试平台与 `v1` 版本均已工作正常。

## 环境依赖

本项目默认面向 Linux 环境，建议至少具备以下工具：

- `verilator`
- `make`
- `gcc` / `g++`
- `python3`

以 Ubuntu 或 Debian 为例，可使用以下命令安装：

```bash
sudo apt-get update
sudo apt-get install -y verilator make g++ python3
```

## 为什么要这样拆

`BigBird` 的设计重点，不是尽快堆出一颗“看起来完整”的 CPU，而是尽量让学习过程本身具备连续性和可解释性。

这套工程主要想避开几种很常见的问题：

- 第一版就引入过多概念，导致理解门槛过高
- 前几版过于简陋，和后续版本之间完全断层
- 每个阶段使用不同测试方式，读者无法建立稳定反馈
- 文档只说明“结果是什么”，但不解释“为什么这样拆”

所以这里采用的是一种比较朴素的思路：

- 保持 `myCPU` 顶层接口稳定，避免学习过程中接口频繁变化。
- 保持 SoC 顶层与测试入口稳定，避免验证方法随阶段漂移。
- 优先控制教学复杂度，而不是过早追求形式上的“完整”。
- 每一版只解决当前阶段最值得解决的问题。
- 通过小步迭代形成连续正反馈，而不是依赖一次性的大爆炸实现。

## 适合谁看

本项目尤其适合以下读者：

- 第一次系统学习处理器设计的本科生或初学者
- 已经学过一点数字逻辑，但对 CPU 仍然缺乏整体图景的读者
- 看过一些“流水线 CPU 教程”，却在第三页就开始怀疑人生的读者

如果你已经能够比较熟练地阅读完整流水线 CPU 源码，那么 `BigBird` 对你的主要价值，可能更多体现在教学组织、实验拆分和课程设计参考上。

## 为什么是 8 个版本

之所以采用 `v1` 到 `v8` 的组织方式，而不是只给出一颗“最终版 CPU”，主要基于以下考虑：

- 处理器设计本身具有清晰层次，适合分阶段呈现
- 单周期与流水线之间存在天然台阶，不宜被粗暴压缩
- 冒险处理和 CSR 属于后期主题，不适合过早打断主线
- 每个阶段都需要独立测试与独立文档，因此版本数不宜过少

简而言之，八个版本不是为了形式上的丰富，而是为了让学习曲线尽量平滑。

## 目录结构

项目核心目录如下：

- `v1` 到 `v8`：八个循序渐进的处理器版本
- `cdp-tests`：统一测试平台，用于单条指令验证与批量回归

每个版本目录一般包含：

- `myCPU.sv`：顶层 CPU
- 若干配套子模块
- 对应版本的 `README.md`

## 版本路线

### v1

最小单周期骨架。

- 聚焦 `myCPU` 顶层接口、PC、取指与调试写回口。
- 保留最小可运行指令子集：`jal`、`addi`、`ecall`。
- 目标是先建立“处理器最基本在做什么”的直觉。

### v2

单周期基础整数与分支子集。

- 引入寄存器堆闭环。
- 加入 `lui`、`auipc`、`add` 与基础分支指令。
- 建立稳定的取指、译码、执行、写回主链路。

### v3

单周期整数 ALU 主线。

- 补齐常见整数算术、逻辑、比较与移位指令。
- 在不引入访存复杂度的前提下，完成整数执行通路。
- 适合作为理解 ALU、立即数和控制选择的关键阶段。

### v4

单周期访存阶段。

- 引入 `perip_*` 访存接口。
- 支持 `lb/lh/lw/lbu/lhu` 与 `sb/sh/sw`。
- 建立数据读写、扩展与掩码控制逻辑。

### v5

完整单周期 RV32I 主线。

- 补齐 `jalr` 与完整控制流。
- 收束为一颗功能闭环明确的单周期 CPU。
- 为后续流水线阶段提供稳定功能基线。

### v6

流水线骨架版。

- 引入 IF/ID/EX/MEM/WB 阶段划分。
- 教学重点是结构拆分，而不是完整性能优化。
- 为保持后续验证链路连续，功能上已保留较完整的系统指令与 CSR 主路径。
- 主要解决“单周期如何演化为流水线”这一问题。

### v7

带冒险处理的流水线版。

- 引入前递、暂停、冲刷等关键控制机制。
- 在 `v6` 的系统指令/CSR 基础上，重点补齐数据冒险与控制冒险处理。
- 让流水线从“结构存在”走向“行为更稳定、更接近真实可用”。
- 适合作为理解 hazard 处理的主版本。

### v8

最终教学收束版。

- 收束为与当前验证平台高度一致的成熟实现。
- 强化访存、前递、回写与系统路径之间的协同细节。
- 作为整套教程的最终回归版本。
- 适合作为继续扩展、优化和课程实验的起点。

## 怎么看这套工程

推荐按以下顺序阅读与实践：

1. 先运行 `v1`，确认环境无误，并建立最小闭环直觉
2. 阅读 `v1` 到 `v2`，理解处理器最基础的数据流动
3. 阅读 `v3` 到 `v5`，吃透单周期数据通路与控制逻辑
4. 阅读 `v6` 到 `v7`，理解流水线拆分与 hazard 处理
5. 最后回到 `v8`，把系统路径与完整验证串起来

如果准备把它作为长期自学或课程项目推进，建议采用“先读 README，再读代码，最后运行测试”的节奏。

## 怎么验证

本项目通过 `cdp-tests` 目录统一执行验证，并使用 `CPU_DIR` 指向目标版本源码。

单条测试示例：

```bash
cd cdp-tests
make clean
make run TEST=simple CPU_DIR=../v1
```

统一测试平台的意义在于：

- 同一套测试入口可以复用于多个教学版本
- 不需要为每个版本单独维护不同验证脚本
- 可以更清楚地观察“同一类测试在不同阶段如何逐步通过”

如果你准备检查最终版本，也可以直接执行批量回归：

```bash
cd cdp-tests
make clean
CPU_DIR=../v8 python3 run_all_tests.py
```

## 学习建议

推荐按照以下顺序学习：

1. `v1` 到 `v2`：建立最小整体感
2. `v3` 到 `v5`：吃透单周期数据通路与控制逻辑
3. `v6` 到 `v7`：理解流水线拆分与冒险处理
4. `v8`：理解系统控制路径与完整回归

不建议跳读。处理器设计最怕的不是代码多，而是“上一层没站稳，下一层已经开始加戏”。

## FAQ

### 为什么早期版本也会出现 `ecall`？

在 `BigBird` 的早期版本中，`ecall` 主要被用作测试平台的统一结束信号，而不是完整展开其异常处理语义。这样做的目的，是在最早阶段就建立一个清晰、稳定、可自动判定的验证闭环。

### 为什么前几个版本的文件数量比后面少？

这是刻意保留的教学节奏控制。前期版本优先压缩模块数量，帮助读者建立整体感；后期版本再逐步引入更多模块划分，使结构复杂度与学习深度同步增长。

### 为什么不从一开始就直接讲完整流水线？

因为那样通常会让初学者同时面对数据通路、控制通路、hazard、flush、stall、前递和异常路径，学习成本过高。`BigBird` 的核心策略是“延后复杂度，而不是回避复杂度”。
